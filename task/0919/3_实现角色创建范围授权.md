一、业务规则（已确定）

1. SUPER_ADMIN 是系统预置根角色，只能由系统初始化逻辑创建；任何用户（包括 SUPER_ADMIN）都不能通过 POST /api/roles 创建 roleCode=SUPER_ADMIN。
2. SYSTEM_ADMIN 是由 SUPER_ADMIN 通过 POST /api/roles 创建的系统管理角色；SYSTEM_ADMIN 本人不能创建 roleCode=SYSTEM_ADMIN。
3. SUPER_ADMIN 可以通过接口创建 SYSTEM_ADMIN 和普通业务角色。
4. SYSTEM_ADMIN 可以通过接口创建普通业务角色，但不能创建 SUPER_ADMIN 或 SYSTEM_ADMIN。
5. SALES_MANAGER、SALES_STAFF 不应拥有 role:create 功能权限；即使有人直接请求接口，也必须经过现有 @PreAuthorize 校验。
6. 普通业务角色不限于 SALES_MANAGER、SALES_STAFF，允许未来使用其他合法自定义 roleCode。不要写死业务角色白名单。
7. 创建角色不等于分配权限。本次不得为新角色自动授予权限，也不得改动角色权限配置接口。

二、实施前先核查

检查 RoleController、RoleServiceImpl、创建角色请求 DTO、SysRole、Mapper、DataInitializer、init.sql、角色相关异常处理和现有测试，确认：
- POST /api/roles 当前的 @PreAuthorize、请求字段及返回状态；
- roleCode 的格式、规范化、重复校验与数据库唯一约束；
- SUPER_ADMIN 和 SYSTEM_ADMIN 的真实初始化或创建路径；
- 当前是否已有保留角色编码或创建范围限制；
- 新角色是否默认无权限；
- 当前如何从 SecurityContext 获取操作者的完整角色集合。

如果发现现有机制与上述规则冲突，先在输出中说明冲突及影响；对于会改变初始化机制、数据库结构或既有 API 契约的冲突，不要自行做扩大范围的修改。

三、实现角色创建范围校验

保留现有方法级功能权限检查，例如 role:create；不要用角色名称检查替代 @PreAuthorize。

在 Service 层、数据库写入前，基于规范化后的 roleCode 和当前认证用户的完整角色集合进行创建范围校验：

- 目标 roleCode 为 SUPER_ADMIN：一律拒绝接口创建。
- 目标 roleCode 为 SYSTEM_ADMIN：仅操作者具有 SUPER_ADMIN 角色时允许继续。
- 目标为其他合法 roleCode：操作者已通过 role:create 功能权限检查后，允许继续执行现有创建流程。

多角色用户只要具有 SUPER_ADMIN，即按 SUPER_ADMIN 的创建范围处理；不要只检查角色集合中的第一个角色。不要根据前端传入的操作者身份或角色字段进行判断。

保持已有 roleCode 格式、重复校验、角色启用状态等规则，不要为了新增授权逻辑而删除或绕过它们。尤其要确保“目标编码不存在”时仍执行范围校验，不能只依赖编码重复检查来阻止创建系统角色。

四、异常与响应

为角色创建范围越权提供明确的业务异常，并映射为 HTTP 403 ProblemDetail。错误码建议使用 ROLE_CREATION_FORBIDDEN；如果项目已有语义相同的异常和错误码，优先复用并说明原因。

保留现有功能权限不足时的 403 FORBIDDEN，以及未认证时的 401 UNAUTHORIZED。角色编码重复、参数非法等情况继续使用项目现有错误响应，不要全部改成 403。

记录必要的安全拒绝日志：包含操作者 ID、目标 roleCode 和拒绝原因；不要记录 JWT、密码等敏感信息，也不要为正常请求添加冗余日志。
