二、接口设计

新增接口：

```http
GET /api/roles/{roleId}/permissions
```

该接口只负责返回：

```text
当前角色拥有的权限 ID
```

推荐返回：

```json
[
  2085985855238352897,
  2085985855238352898,
  2085985855238352899
]
```

或者：

```json
{
  "permissionIds": [
    2085985855238352897,
    2085985855238352898
  ]
}
```

具体选择必须遵守当前项目已有 API 返回结构。

不要重新返回完整 PermissionTree。

完整权限树继续由：

```http
GET /api/permissions
```

负责。

职责必须保持：

```text
GET /api/permissions
= 系统有哪些权限

GET /api/roles/{roleId}/permissions
= 当前角色拥有哪些权限
```

五、RoleServiceImpl

实现权限 ID 查询。

核心关系：

```text
sys_role
      │
      │ role_id
      ↓
sys_role_permission
      │
      │ permission_id
      ↓
sys_permission
```

本次最基本查询是：

```sql
SELECT permission_id
FROM sys_role_permission
WHERE role_id = ?
```

但请结合当前数据库和实体设计判断是否还需要过滤：

```text
sys_permission.status = 1
sys_permission.deleted = 0
```

如果 `sys_permission` 存在逻辑删除和启停状态，而角色权限关系表中可能残留失效 permission_id，则建议最终只返回当前有效权限。

但是不要过度复杂化。

如果项目已经保证删除权限时同步清理关系，或者权限不会物理删除，可以直接查询关系表。

优先使用 MyBatis-Plus，例如：

```java
lambdaQuery()
    .eq(SysRolePermission::getRoleId, roleId)
```

或者通过已有 SysRolePermissionMapper 查询。

不要为了简单查询写不必要的 XML。

九、TypeScript Long ID 问题

这是本次必须重点检查的地方。

当前数据库角色 ID 和权限 ID 使用 MyBatis-Plus Snowflake Long，例如：

```text
2085985855238352897
```

这已经超过 JavaScript：

```text
Number.MAX_SAFE_INTEGER
```

因此必须检查当前项目后端对 Long 的 JSON 序列化方式。

如果当前 API 已经将 Long 序列化为字符串：

```json
[
  "2085985855238352897",
  "2085985855238352898"
]
```

前端必须继续使用：

```ts
string
```

不要转成 Number。

如果项目当前 ID 类型在前端已经统一为 string，请严格保持：

```ts
type PermissionId = string
```

绝对不要：

```ts
Number(permissionId)
parseInt(permissionId)
```

否则 Snowflake ID 可能发生精度丢失，最终导致：

```text
setCheckedKeys()
找不到树节点
```

请检查当前权限树返回的 id 类型和角色权限 ID 返回类型，保证二者完全一致。

十三、父子节点回显问题

Element Plus Tree 的：

```ts

```

涉及父子联动，这是本次必须重点验证的问题。

当前权限树可能类似：

```text
系统管理
├── 用户管理
│   ├── user:list
│   ├── user:create
│   ├── user:update
│   └── user:delete
├── 角色管理
│   ├── role:list
│   ├── role:create
│   └── ...
└── 权限管理
```

需要检查当前：

```vue
<el-tree
  ...
  show-checkbox
  ...
/>
```

是否启用了：

```text
check-strictly
```

如果没有启用，则父子节点存在联动。

本次不要随意改变现有权限树的父子选择语义。

但是需要确保：

```text
数据库中已有 permission_id
```

回显后与数据库真实权限含义一致。

特别注意一种问题：

如果数据库只保存叶子权限，但：

```ts

```

给父节点 ID 后可能自动勾选全部子节点。

请基于当前 sys_permission 数据结构和已有权限保存设计，判断：

```text
关系表到底保存全部 checked 节点
还是只保存叶子权限节点
```

本次不要自行更改数据模型，只保证与现有设计一致。

如果当前“权限保存”尚未实现，因此无法确定最终保存策略，则：

```text
回显严格按照 sys_role_permission 中已有 permission_id
```

不要自行补齐不存在的 ID。

