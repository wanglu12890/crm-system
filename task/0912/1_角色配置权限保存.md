基于当前 CRM 项目已有代码，实现“角色管理 → 配置权限 → 权限保存”。

当前阶段：

```text
新建角色                  ✅
权限树展示                ✅
权限回显                  ✅
权限保存                  ← 本次
新建用户 + 绑定角色
权限控制差异
阶段测试
```

当前已经实现：

```text
GET /api/permissions
→ 查询完整权限树

GET /api/roles/{roleId}/permissions
→ 查询当前角色已有 permissionId[]
→ RolePermissionDialog.vue
→ setCheckedKeys(permissionIds)
→ 完成权限回显
```

本次目标：

```text
用户在 RolePermissionDialog 中调整权限
↓
点击“保存”
↓
获取当前真正勾选的 permissionIds
↓
PUT /api/roles/{roleId}/permissions
↓
后端校验
↓
删除该角色旧权限关系
↓
批量插入新权限关系
↓
事务提交
↓
返回成功
↓
前端提示“权限保存成功”
```

本次只实现角色权限保存。

不要实现：

```text
新建用户
用户绑定角色
权限差异控制
@EnableMethodSecurity
@PreAuthorize
动态菜单
按钮权限
```

这些放在后续阶段。

二、先确定权限保存策略

当前 Element Plus Tree：

```text
show-checkbox = true
check-strictly = false
```

即父子联动。

请检查当前 `sys_permission` 的 15 个节点真实结构。

本次默认优先采用：

```ts
treeRef.getCheckedKeys()
```

作为保存集合。

不要默认把：

```ts
getHalfCheckedKeys()
```

加入保存集合。

理由：

```text
完全选中节点
→ 代表用户明确拥有该权限

半选父节点
→ 只是因为部分子节点被选中
→ 不应自动等价为完整父级权限
```

但是请根据项目当前权限树数据进一步检查：

如果父级目录 / 菜单节点必须存在于 `sys_role_permission` 中，才能保证后续菜单显示逻辑正常，则可以调整策略。

如果当前项目尚未实现动态菜单，因此父级节点是否必须保存还没有明确业务依赖，则保持最简单策略：

```text
只保存 getCheckedKeys()
不保存 getHalfCheckedKeys()
```

不要自行扩展复杂权限模型。

三、接口设计

新增接口：

```http
PUT /api/roles/{roleId}/permissions
```

请求体建议：

```json
{
  "permissionIds": [
    "2085985855238352897",
    "2085985855238352898",
    "2085985855238352899"
  ]
}
```

由于 Snowflake ID 已统一：

```text
Java Long
↓
JSON string
↓
TypeScript string
```

前端继续发送字符串 ID。

后端可以正常反序列化为：

```java
List<Long>
```

具体根据当前 Jackson 配置验证。

接口语义：

```text
用当前提交的 permissionIds
完整替换该角色现有权限
```

不是增量添加。

即：

```text
旧权限 = A B C

新提交 = A D

最终数据库：
A D
```

而不是：

```text
A B C D
```

四、新增请求 DTO

新增类似：

```text
UpdateRolePermissionsDTO.java
```

字段：

```java
private List<Long> permissionIds;
```

如果项目命名风格更适合：

```text
SaveRolePermissionsDTO
AssignRolePermissionsDTO
```

可保持现有项目风格。

要求：

```text
permissionIds 允许空数组
```

因为：

```text
[]
```

代表：

```text
清空该角色所有权限
```

不要使用：

```java
@NotEmpty
```

阻止空数组。

但如果整个字段为：

```text
null
```

建议视为参数错误。

可以使用：

```java
@NotNull
```

五、Controller

在 RoleController 中新增：

```java
@PutMapping("/{roleId}/permissions")
```

职责：

```text
接收 roleId
接收 UpdateRolePermissionsDTO
参数校验
调用 roleService.updateRolePermissions(...)
返回统一成功响应
```

不要直接操作 Mapper。

例如语义：

```java
roleService.updateRolePermissions(roleId, dto.getPermissionIds());
```

返回类型继续遵守当前项目统一规范。

六、Service

在 RoleService 中新增：

```java
void updateRolePermissions(Long roleId, List<Long> permissionIds);
```

或按现有风格调整返回类型。

本次核心业务全部放在 ServiceImpl。

七、必须使用事务

本次操作包含：

```text
DELETE 旧关系
+
INSERT 新关系
```

属于一个完整业务操作。

必须保证原子性。

在 ServiceImpl 方法增加：

```java
@Transactional
```

核心含义：

```text
删除旧关系成功
↓
插入新关系过程中失败
↓
整个事务回滚
↓
旧权限不能被错误清空
```

这是本次开发需要重点验证的地方。

八、ServiceImpl 核心流程

推荐执行顺序：

```text
1. 校验角色存在
2. permissionIds 去重
3. 校验 permissionIds 合法
4. 删除该角色旧权限
5. 批量插入新权限
6. 记录成功日志
```

九、角色存在校验

建议本次正式增加最基本的角色存在判断。

例如：

```text
sys_role.id = roleId
AND deleted = 0
```

不存在则抛出项目现有合适异常。

如果当前项目仍没有统一 NotFound 异常基类，可以实现最小范围异常处理。

错误语义例如：

```text
角色不存在
```

不要允许：

```text
不存在的 roleId
↓
直接向 sys_role_permission 写入孤儿关系
```

十、permissionIds 去重

前端即使重复提交：

```json
[
  "1001",
  "1001",
  "1002"
]
```

后端也应该先去重。

可以使用：

```java
distinct()
```

或 Set。

最终插入：

```text
1001
1002
```

避免唯一约束冲突或重复数据。

十一、权限有效性校验

不能盲目信任前端提交的 permissionIds。

至少验证：

```text
permission ID 是否真实存在
status 是否为 1
```

当前 `sys_permission` 没有 deleted 字段，所以不需要逻辑删除条件。

推荐：

```text
提交 5 个 permissionIds
↓
查询数据库有效权限
↓
有效权限数也必须为 5
```

如果发现无效 ID：

```text
拒绝整个保存请求
```

不要静默忽略无效权限。

例如：

```text
提交：
A B INVALID

不能最终保存：
A B
```

应该整体失败并回滚。

异常信息清晰即可，例如：

```text
存在无效或已禁用权限
```

十三、批量插入新权限

如果：

```text

```

则：

```text

↓
不执行 insert
↓
事务提交
```

最终该角色无权限。

如果非空，则批量插入：

```text
role_id
permission_id
```

请检查 `sys_role_permission` 表是否还包含：

```text

```

等字段。

必须根据真实表结构填充。

如果中间表只有：

```text

```

则不要凭空增加字段。

如果有主键 ID 且实体使用：


如果 MyBatis-Plus 当前版本支持项目已有批量保存方式，可以使用现有方式。
