注意：不要大范围重构现有项目，优先复用当前已有的 RoleController、RoleService、RoleServiceImpl、SysRoleMapper、SysRole 实体、前端 Role.vue、RoleDialog.vue、api/role.ts，以及项目现有的统一请求、异常处理、日志规范和返回结构。

```text

角色名称：系统管理员
角色编码：SYSTEM_ADMIN
状态：启用
备注：负责系统用户及普通角色管理
```

创建成功后，角色列表应自动刷新并显示 SYSTEM_ADMIN。

请先只读检查当前项目已有实现，重点确认：

```text

```

不要根据假设自行新增与现有项目冲突的架构。

检查完成后直接继续开发，不需要停下来询问。

在合适的 dto/role 目录新增：

三、后端：POST /api/roles

在现有 RoleController 中增加新建角色接口。

接口：

```http
POST /api/roles
```

请求示例：

```json
{
  "roleName": "系统管理员",
  "roleCode": "SYSTEM_ADMIN",
  "status": 1,
  "remark": "负责系统用户及普通角色管理"
}
```

Controller 只负责：

```text
接收参数
↓
参数校验
↓
调用 roleService.createRole()
↓
按照项目统一格式返回结果
```

不要在 Controller 中编写数据库查询和业务规则。

如果当前项目已经具备权限控制能力，则为该接口增加：

```java
@PreAuthorize("hasAuthority('role:create')")
```

但前提是当前项目的权限加载链路确实已经可用。

不要为了本功能重新设计整个 Spring Security。

四、后端：RoleService

在 RoleService 中增加：

```java
createRole(CreateRoleDTO dto)
```

具体返回类型根据项目当前规范决定。

如果项目业务新增操作通常返回 Long、SysRole、DTO 或 void，请保持一致，不要另起一套风格。

五、后端：RoleServiceImpl 核心业务

新建角色的核心逻辑全部放在 RoleServiceImpl。

执行顺序：

```text
1. 参数规范化
2. 校验 roleCode 唯一
3. 获取当前登录用户
4. DTO 转 SysRole
5. 设置必要默认字段
6. 插入数据库
7. 记录关键业务日志
```

1）roleCode 唯一校验

查询：

```text
sys_role.role_code = dto.roleCode
```

如果项目使用逻辑删除，需要结合：

```text
deleted = 0
```

判断当前有效角色是否已经存在。

如果 roleCode 已存在：

```text
禁止创建
抛出项目现有业务异常
返回清晰错误信息，例如：
“角色编码 SYSTEM_ADMIN 已存在”
```

数据库唯一约束仍然保留，Service 层的业务校验用于提供更友好的错误信息。

注意：

```text
不要把该业务校验写进 SysRoleMapper
```

Mapper 只负责数据访问。

2）获取当前登录用户

优先复用 Spring Security 当前上下文：

```java
Authentication authentication =
        SecurityContextHolder.getContext().getAuthentication();

String username = authentication.getName();
```

用于 createdBy / updatedBy。

如果当前项目已经有统一的 SecurityUtils、UserContext 或其他工具类，则优先使用已有封装，不重复造轮子。

3）组装 SysRole

从 DTO 设置：

```text
roleName
roleCode
status
remark
```

其他字段必须结合当前 SysRole 实体和数据库结构决定。

重点检查：

```text
id
dataScope
createdBy
createdAt
updatedBy
updatedAt
deleted
version
```

处理规则：

id：

如果 SysRole 已使用类似：

```java
@TableId(type = IdType.ASSIGN_ID)
```

则不要手工生成 ID，让 MyBatis-Plus 自动生成。

createdBy：

```text
当前登录 username
```

updatedBy：

新建时可以与 createdBy 相同。

createdAt / updatedAt：

如果项目已有 MyBatis-Plus MetaObjectHandler 自动填充，继续使用自动填充。

如果尚未实现自动填充，则当前版本允许在 Service 中使用：

```java
LocalDateTime.now()
```

设置创建和更新时间。

不要为了本功能单独引入复杂的自动填充架构。

deleted：

按照数据库默认值或项目当前逻辑删除规则处理。

version：

按照数据库默认值或当前乐观锁设计处理。

dataScope：

先检查当前数据库字段和已有角色数据。

如果数据权限功能尚未真正实现，则使用项目已有合理默认值，不在本次扩展数据权限功能。

七、日志要求

这是以后 CRM 开发需要持续遵守的开发习惯，本次也必须执行。

请先检查项目现有日志写法，例如：

```java
@Slf4j
```

并保持统一。

本功能至少考虑以下日志。

创建成功：

```java
log.info(...)
```

建议记录：

```text
操作类型：createRole
操作用户 username
新角色 roleCode
新角色 roleName
新角色 id
```

示意：

```java
log.info(
    "Create role success, operator={}, roleId={}, roleCode={}, roleName={}",
    username,
    role.getId(),
    role.getRoleCode(),
    role.getRoleName()
);
```

角色编码冲突：

根据项目规范选择 info 或 warn。

建议：

```java
log.warn(
    "Create role rejected: roleCode already exists, operator={}, roleCode={}",
    username,
    dto.getRoleCode()
);
```

数据库或未知异常：

如果项目已经通过全局异常处理统一记录异常，则不要重复大量打印堆栈。

避免：

```text
Controller 打一次
Service 打一次
GlobalExceptionHandler 又打一次
```

造成重复日志。

日志原则：

```text
INFO：
重要业务操作成功

WARN：
业务异常、权限拒绝、重复数据、非法状态等值得关注但系统仍正常运行的问题

ERROR：
真正的系统异常、数据库异常、不可预期异常
```

禁止记录：

```text
密码
JWT Token
Authorization Header
数据库密码
完整敏感个人信息
```

不要为了“有日志”而在普通 getter、Mapper 查询等位置大量打印无意义日志。
