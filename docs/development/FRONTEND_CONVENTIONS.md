# CRM 前端开发规范（V1）

## 1. 适用范围

本规范适用于 CRM 系统所有 Vue3 前端页面的新增、修改与重构。

技术栈：Vue3、TypeScript、Element Plus、Pinia、Vue Router、Axios。

开发前必须先检查现有相似业务模块，优先遵循项目已经形成的组件组织、页面风格和代码规范。

本规范用于指导组件设计，不要求所有页面机械地使用相同结构。

## 2. 页面组织原则

对于典型的业务管理页面，优先采用：

**页面容器（View）+ 功能子组件（Components）**

例如：

```text
Customer.vue
├── CustomerSearch.vue
├── CustomerTable.vue
├── CustomerFormDialog.vue
└── CustomerDetailDialog.vue
```

各组件按业务职责拆分，而不是简单按代码行数或 HTML 标签拆分。

即使某个页面当前业务简单，如果已明确存在后续扩展需求，也应优先建立合理的组件边界，避免后续反复重构。

## 3. 组件职责划分

### 3.1 页面容器：xxx.vue

主要负责：

- 页面级数据与状态管理
- API 查询和数据加载
- 查询条件与分页协调
- 子组件事件处理
- Dialog 打开与关闭协调
- 新建、编辑成功后的列表刷新

不应包含大量表格列定义、复杂表单和多个业务对话框的完整实现。

### 3.2 查询组件：xxxSearch.vue

主要负责：

- 查询表单展示
- 查询字段状态与交互
- 查询和重置操作
- 向父组件发送 search/reset 事件

原则上不直接调用列表查询 API。

查询条件变化后的服务端请求及分页重置由页面容器协调。

### 3.3 表格组件：xxxTable.vue

主要负责：

- 表格数据展示
- 枚举及状态展示
- 操作按钮展示
- 表格 loading 状态
- 向父组件发送 view/edit/delete 等操作事件

通过 props 接收数据，通过 emits 通知父组件。

原则上不负责列表 API 查询、页面分页状态及 Dialog 的打开。

### 3.4 表单组件：xxxFormDialog.vue

主要负责：

- 表单展示
- 新建/编辑模式
- 表单初始化与回显
- 字段校验
- 表单提交
- 提交 loading
- 成功/失败交互

对于新建和编辑字段高度重合的业务，优先考虑共用一个 FormDialog。

当表单构成完整独立业务交互时，可以由 Dialog 自己调用创建/更新 API，成功后通过 success 事件通知父页面刷新列表。

### 3.5 详情组件：xxxDetailDialog.vue

主要负责业务详情展示和必要的数据加载。

如果详情内容复杂、需要独立路由或包含多个业务子模块，可以使用独立详情页面，不强制采用 Dialog。

## 4. 父子组件通信

优先使用 Vue3 标准方式：

- 父组件通过 props 传递数据
- 子组件通过 emits 通知操作
- 表单双向绑定按实际需求使用 v-model
- Pinia 用于跨页面共享状态，不用于替代普通父子通信

遵循：

**数据由合适的组件管理，事件由真正负责该业务的组件处理。**

避免不必要的多层事件转发和过度状态提升。

## 5. 查询与分页

遵循实际后端接口设计。

对于服务端分页页面：

- 页面容器维护 page、size、total
- 查询条件和数据范围由后端处理
- 查询条件变化后重置到第一页
- 页码或 pageSize 变化时重新请求后端
- 表格直接展示后端返回的 records
- 不对当前页 records 再进行业务分页或全局筛选

不允许前端绕过后端数据权限。

对于明确采用前端分页的现有小型管理页面，可以保留既有实现，不强制立即重构。

## 6. 权限控制

复用项目现有 Pinia、权限工具及按钮权限机制。

前端负责菜单、按钮和交互展示控制。

后端负责真正的接口权限、对象权限和数据范围控制。

不得在前端自行实现 ALL / DEPT / SELF 数据过滤，也不得以隐藏按钮代替后端授权。

## 7. UI 与代码风格

新增页面应优先参考现有 User、Role、Customer 等已完成模块。

保持以下方面一致：

- 页面布局与间距
- 查询区排列
- 按钮样式
- Element Plus 表格风格
- Dialog 风格
- 分页位置
- Loading、Empty、错误提示
- TypeScript 类型和 API 文件组织方式

优先复用现有工具、类型和枚举映射，不重复造轮子。

## 8. 避免过度组件化

不要求每个按钮、输入框、表格列或分页控件都单独封装。

简单、独立、没有明显扩展需求的页面，可以保留单文件实现。

组件拆分应至少满足以下目标之一：

- 具有独立明确的职责
- 能降低页面容器复杂度
- 有较明确的复用需求
- 有后续业务扩展需求
- 与项目已有成熟组织方式保持一致

不要为了统一命名而创建大量无实际价值的组件。

## 9. Codex 开发要求

每次新增前端业务页面前：

1. 阅读 CODEX_CONTEXT.md 和本规范。
2. 检查现有相似业务模块。
3. 确认本次页面的组件结构和职责边界。
4. 优先按既定结构实现，而不是先将全部逻辑写进 View。
5. 保持现有 API、权限、查询和分页行为。
6. 不进行无关重构。
7. 完成后检查 TypeScript、构建及主要交互。
8. 在执行报告中说明新增组件及职责划分。

如果实际业务与本规范不适配，应说明原因并采用更简单合理的实现，不必机械遵守。
