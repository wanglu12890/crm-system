# CRM 系统架构设计

## 1. 总体架构

系统采用前后端分离的模块化单体架构。Vue SPA 只负责展示与交互，通过 HTTPS/JSON 调用 Spring Boot REST API；后端集中处理认证、授权、业务规则、事务和持久化。第一阶段选择模块化单体，可降低部署与分布式事务复杂度，同时用清晰的模块边界为后续服务拆分保留空间。

生产环境建议采用 `Nginx -> frontend 静态资源 / backend API -> MySQL`，密钥与数据库凭据仅通过环境变量或密钥管理系统注入。

## 2. 目录与职责

### 后端

| 目录 | 职责 | 企业级划分原因 |
|---|---|---|
| `controller` | 接收 HTTP 请求、参数校验、权限入口、返回统一响应 | 隔离协议层，不承载业务规则 |
| `service` | 业务能力接口、用例编排、事务边界 | 便于测试、复用与替换实现 |
| `service/impl` | Service 实现，组合 Mapper 和领域规则 | 接口与实现分离，避免调用方依赖细节 |
| `mapper` | MyBatis-Plus Mapper 与复杂查询接口 | 集中数据访问，避免 SQL 渗透到业务层 |
| `entity` | 数据库表映射对象 | 只描述持久化结构，不直接作为 API 契约 |
| `dto` | 请求参数、查询条件、服务命令 | 防止越权字段绑定，承载参数校验 |
| `vo` | 返回给前端的视图模型 | 屏蔽密码、内部状态等字段，稳定接口契约 |
| `config` | MyBatis、Jackson、Web、跨域等配置 | 基础设施配置集中治理 |
| `security` | JWT、Security Filter、认证主体、鉴权处理器 | 安全横切逻辑与业务代码解耦 |
| `exception` | 业务异常、全局异常处理、错误码映射 | 形成统一且可观测的错误协议 |
| `utils` | 无状态、无业务含义的工具 | 避免重复代码；禁止演变为万能类集合 |
| `common` | 统一响应、分页、常量、基类 | 统一跨模块契约，减少重复定义 |
| `resources/mapper` | 复杂 SQL XML | Java 接口与 SQL 分离，便于审查与调优 |

业务增长后，应在以上分层下按 `auth/customer/contact/lead/opportunity/followup/contract/statistics/system` 再分包，避免所有模块类平铺。

### 前端

| 目录 | 职责 | 企业级划分原因 |
|---|---|---|
| `api` | 按业务模块封装后端接口 | 页面不感知 URL 与 Axios 细节 |
| `assets` | 样式、字体、图片等静态资源 | 统一构建与缓存管理 |
| `components` | 可复用的无业务/弱业务组件 | 降低页面重复，提高一致性 |
| `layouts` | 主框架、登录、空白布局 | 页面内容与导航骨架解耦 |
| `router` | 静态路由、动态权限路由、守卫 | 集中处理登录态和页面权限 |
| `stores` | Pinia 全局状态 | 登录用户、权限、字典等跨页面共享 |
| `views` | 按业务模块组织页面 | 页面与业务边界一一对应 |
| `utils` | Axios、缓存、日期等通用能力 | 统一错误、超时、Token 处理 |
| `types` | API、公共组件、环境类型 | 让前后端契约可检查、可重构 |

## 3. 后端分层与数据流

- Controller：只做协议转换、Bean Validation、调用 Service 和响应组装；禁止直接调用 Mapper。
- Service：校验业务前置条件、执行授权范围判断、编排多个数据操作，并用 `@Transactional` 保证一致性。
- Mapper：执行单表 CRUD、分页及经评审的关联查询；不承载业务决策。
- Entity：与表结构映射，包含主键、审计字段、乐观锁/逻辑删除字段；不得向浏览器直接暴露。
- DTO：面向“输入”，如 `CustomerCreateDTO`、`CustomerQueryDTO`；字段由用例决定并使用校验注解。
- VO：面向“输出”，如 `CustomerDetailVO`；可组合多表数据和脱敏字段，不与 Entity 强绑定。

完整链路：

`Vue View -> api 模块 -> Axios 拦截器附加 Bearer Token -> Security JWT Filter -> Controller DTO 校验 -> Service 权限/业务/事务 -> Mapper -> MyBatis-Plus -> MySQL -> Entity/投影 -> Service 转 VO -> 统一 Result -> Axios 响应拦截器 -> Pinia/View`

异常在后端由全局异常处理器转换为标准错误码；401 触发前端刷新 Token 或退出，403 展示无权限，业务错误展示可读消息。

## 4. 核心业务模块

| 模块 | 核心职责 | 关键边界 |
|---|---|---|
| 用户认证 | 登录、退出、Token 刷新、当前用户 | 密码 BCrypt；短期 Access Token + 可撤销 Refresh Token |
| 客户管理 | 客户建档、分配、共享、标签、生命周期 | 客户名称/联系方式去重，负责人数据权限 |
| 联系人管理 | 客户联系人、主联系人、联系方式 | 联系人必须归属客户，敏感字段脱敏 |
| 线索管理 | 线索录入、分配、领取、转化 | 转化客户/联系人/商机需同一事务防重复 |
| 商机管理 | 销售阶段、预计金额、赢单/输单 | 阶段变更留痕，金额用 DECIMAL |
| 跟进记录 | 对客户/线索/商机的沟通记录和计划 | 多态业务对象约束由 Service 保证，禁止物理删除审计记录 |
| 合同管理 | 合同、金额、期限、审批状态 | 合同编号唯一，状态机限制非法变更 |
| 数据统计 | 漏斗、业绩、转化率、趋势 | 按组织和数据权限聚合，大查询只读化/缓存化 |
| 系统管理 | 用户、角色、权限、组织、字典、日志 | RBAC 控制功能权限，组织结构控制数据范围 |

## 5. 横切规范

- 主键使用 `BIGINT`（雪花 ID），金额使用 `DECIMAL(18,2)`，时间使用 `DATETIME(3)`。
- 所有业务表包含创建人、更新人、创建时间、更新时间、逻辑删除；高并发更新可增加 `version`。
- 认证采用 Spring Security 无状态模式；接口权限采用 RBAC，数据权限在 Service/查询条件中执行。
- 不在日志记录密码、完整 Token、身份证和完整手机号；关键变更进入审计日志。
- Controller、Service、Mapper 分别做 Web、单元、数据层测试；核心链路补充集成测试。
