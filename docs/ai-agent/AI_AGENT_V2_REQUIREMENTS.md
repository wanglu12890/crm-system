# CRM AI 智能分析 V2.0：客户跟进关注与辅助建议正式 PRD

## 1. 版本信息与背景

- 版本：**V2.0**，2026-10-18；状态：**需求已确认，待设计实现**。已完成R1数据审查及三轮人工业务评审，不代表V2已开发或验收。
- V1统计闭环及V1.1范围优化已完成并验收。本次仅冻结需求基线，不实施V2架构、接口、工具、代码或数据库变更，不改变V1/V1.1角色及统计规则。
- 依据：[数据可行性报告](AI_AGENT_V2_FEASIBILITY_REPORT.md)、当前源码/真实只读SQL、[V1/V1.1需求](AI_AGENT_V1_REQUIREMENTS.md)及[版本记录](AI_AGENT_V1_1_CHANGELOG.md)。旧文档和任务背景中“跟进基础模块已具备”不能理解为完整业务API：当前有follow_record表及权限码，但无FollowRecord生产Entity/Mapper/Service/Controller；客户详情仍待实现。

## 2. 需求目标

基于客户等级、建档时间及有效跟进历史，帮助销售人员识别需优先联系的客户，帮助经理关注本部门覆盖情况，展示可核验原因并给出需人工判断的下一步建议。

产品定位为**可解释的客户跟进关注规则与辅助建议**。不输出流失/成交预测概率，不自动分配客户、修改信息或创建跟进；不把“时间长”“INACTIVE”“无计划”直接等同流失或违规。合成数据只验证可计算性，不证明规则有效。

成功目标：同一数据快照、分析时间和规则版本下Java判定确定；用户看得到授权范围内的关注结果、命中原因和数据来源，能区分低关注、无匹配、特殊状态与服务失败；Qwen仅基于可信结构化事实生成建议，不增加或改写客户事实。

## 3. 用户角色与使用场景

### 3.1 角色、权限与范围

V2仅允许一个有效角色且符合下表的销售用户。必须同时具备`ai:analysis`、`customer:list`、`follow:list`；缺少任一权限即拒绝。角色与最大授权范围不匹配、多有效角色或未知角色均拒绝，默认请求也不能绕过V2准入。不修改现有V1/V1.1规则或角色绑定。

| 角色 | V2准入 | 范围要求 |
|---|---|---|
| SALES_STAFF | 允许，须具备三权限 | 最大授权SELF；默认及显式请求均仅SELF |
| SALES_MANAGER | 允许，须具备三权限 | 最大授权DEPT；默认DEPT，允许显式SELF及DEPT，不允许ALL |
| SYSTEM_ADMIN | 拒绝 | 不继承V1的ALL统计资格 |
| SUPER_ADMIN | 拒绝 | 即使具备三权限也不开放V2 |
| 多有效角色/未知角色/配置不符 | 拒绝 | CURRENT_AUTHORIZED不能旁路业务准入，不扩展组合授权 |

### 3.2 典型问题与可行性

| 用户问题 | 拟提供结果 | 当前支持及依赖 |
|---|---|---|
| 哪些客户需要优先跟进？ | 授权范围内高/中关注清单、原因与排序 | 范围与阈值已确认；安全读取能力待实现 |
| 我负责的客户中有哪些长期没有跟进？ | SELF最近跟进间隔/无记录候选 | follow_at可计算；不能只按本人的跟进记录筛历史 |
| 本部门有哪些高等级客户需要关注？ | DEPT内等级筛选及关注结果 | 等级字段可用；A级采用专属阈值，B级不得误套A级阈值；不得把其他等级静默称为高等级 |
| 为什么这个客户被标记为高关注？ | 单客户命中证据、阈值、日期、参考时间 | 有数据；每次按客户ID重新授权，不依赖已有详情API |
| 针对这些客户下一步怎么跟进？ | 可信指标驱动的通用辅助建议 | 有条件支持；模型输入最小化、事实校验、失败退化待落实 |

业务流程：识别请求语义 → 校验V2准入/三权限与范围 → 限定POTENTIAL/ACTIVE有效已分配客户 → Java计算指标/规则 → 按查询模式筛选、去重、排序并计数 → 分页 → 对当前页必要结果生成建议并展示。这里描述业务责任边界，不确定实现类名、工具数量或接口签名。

## 4. 功能需求

### 4.1 关注客户识别

- 基于统一分析时间T，在第5.1节的适用客户集合内计算关注状态，不以模型输出决定客户集合。
- 首版包含：有效历史的分等级跟进间隔、从未跟进的建档时长及其可解释原因；按第5.2节默认阈值分级。
- “新建未跟进”可以成立；“新分配/新领取后未跟进”缺少事件时间，首版不支持，不能改用created_at冒充。
- 计划逾期正式判定不在V2.0范围内，next_follow_at不参与本版分级、原因、筛选或排序。
- 未匹配到候选时明确显示0个匹配；权限不足、数据不可用或查询失败不以空清单伪装。

### 4.2 等级、特殊状态、原因与排序

- 正常风险等级只有高关注、中关注、低关注；观察中、数据待核验是特殊业务状态，不是第四/第五个风险等级，也不是风险概率。
- 每个命中原因应包含规则描述、观测值、阈值、业务时间来源及分析时间；多个命中原因完整保留，同一客户只计一次。
- 规则版本、有效范围与实际返回条数/匹配总量应可辨认；规则命中数允许重叠，不能相加当客户总数。
- 正常风险结果依次按：①高关注、中关注、低关注；②客户等级A、B、C、D、未评级；③超过当前关注等级起始阈值的完整天数降序；④客户ID稳定排序。不能把超期程度置于客户等级之前。
- 令d为距当前规则时间锚点的完整天数，s为当前等级的起始阈值，超期天数为`d-s`，不得为负或无限大。有历史：A级中/高起点14/30，其他等级中/高起点30/60，低关注起点0；无历史：中/高起点7/14，锚点为建档时间而非伪造的跟进时间。等于阈值时超期天数为0。
- 观察中与数据待核验不参加正常风险等级排序；全状态查询中的独立分区/排列和ID升降方向留D1统一约定，不能改变上述正常结果优先级。

### 4.3 默认查询与分页

- “哪些客户需要优先跟进”等默认关注查询仅匹配高关注和中关注；低关注、观察中、数据待核验不混入默认结果。
- 用户明确查询全部客户关注状态时，可展示适用集合内的低关注及特殊状态，仍排除INACTIVE、公海和删除客户；“全部状态”不是全部生命周期状态或ALL组织范围。
- 默认每页20条，最大每页50条。先完成可信筛选、客户去重、正常风险排序及匹配总量计算，再分页，不在取页后才判级或局部排序。
- 总匹配数与当前页返回数明确区分；多规则命中同一客户只计一次。特殊状态以真实业务状态展示，不冒充需要优先跟进的风险客户。

### 4.4 原因解释与辅助建议

- 单客户原因先用Java可信事实即可展示，Qwen不改写判定。
- 建议基于已提供的等级、状态、跟进间隔、命中原因等结构化事实，给出待人工确认的联系目标、需核实的问题及沟通动作。
- 不得编造联系人、联系方式、预算、采购意向、承诺、最近对话或下次约定时间；缺少信息应建议先核实，不擅自归因“客户无意愿”。
- 不自动执行建议，不写客户或跟进记录；生成失败/不可用时保留可信规则结果，明确“建议暂不可用”，不返回伪造文本。
- Qwen仅接收当前页必要结果的最小结构化指标，不默认提供跟进正文、联系方式、详细地址、客户备注全文及其他非必要敏感信息；不为建议扩大数据读取范围。
- 模型不得修改Java计算的客户事实、关注等级、时间、原因及排序。首版仅对当前页必要结果生成建议，不采用无界逐客户模型调用。

### 4.5 范围与结构化展示

- 显示实际查询范围、分析时间、口径、规则版本、客户标识/名称/等级、关注等级、最近跟进或无记录原因、匹配原因及建议来源。
- 清单字段是功能需求而非冻结JSON契约；敏感联系方式、地址、全文历史默认不展示或传模型。
- 按第4.3节20/50条分页要求区分总匹配数与当前返回数，不得把截断清单称作全部；性能预算留D1测量，不重新把已确认分页值列为待定。
- 不假定已有客户详情/跟进页面；点击客户或请求原因的交互依赖安全只读能力，不能跳转不存在的入口。
- 临时会话不充当授权凭据，不引入持久化或跨轮授权记忆；ID和旧结果都不能跳过再次授权，具体页面组织留D1设计。

## 5. V2.0业务规则与配置基线

### 5.1 统一口径

| 项目 | 已确认口径 | 说明 |
|---|---|---|
| 客户总体 | 当前实际授权范围内deleted=0、owner_id非空，且status为POTENTIAL或ACTIVE | 排除INACTIVE、公海及逻辑删除；全状态查询也遵守该集合 |
| 跟进关联 | target_type=CUSTOMER且target_id=customer.id、deleted=0 | 结构事实；不能使用不存在的follow_record.customer_id |
| 业务时间 | follow_at，不使用记录created_at或客户updated_at替代 | 已有独立字段及36条不同时间样本支持 |
| 最近一次 | 按客户全部有效历史的最大follow_at；同时间按id稳定选择 | 不限跟进人员，包含当前客户可见范围内的前负责人历史；不按记录创建人过滤 |
| 分析参考时间 | 单次请求由后端固定T，Asia/Shanghai | 客户端/模型不能覆盖；本版仅当前快照 |
| 截至T | follow_at≤T，异常未来记录单列；早于建档的记录先待核验 | 不套用V1“本月创建客户”过滤最近跟进历史 |
| 间隔天数 | 满24小时的时长取整；阈值比较anchor≤T−N天，等于阈值算命中 | 不以跨自然日数替代实际时长 |

风险盘点使用截至T的完整有效历史，与V1按客户created_at筛选统计窗口不同。V2.0只支持当前风险快照，不支持历史风险回溯；“本月风险”等不能直接复用V1时间枚举过滤历史并改变口径。意图不明确时应澄清或受控拒绝，不能伪造历史快照。

### 5.2 已有有效跟进历史：默认阈值

时间锚点为最近一次有效follow_at，d为距该时间的完整24小时天数。未评级与B/C/D使用同一组默认阈值，不因为等级缺失自动升降级。

| 客户等级 | 低关注 | 中关注 | 高关注 |
|---|---|---|---|
| A | d < 14 | 14 ≤ d < 30 | d ≥ 30 |
| B、C、D、未评级 | d < 30 | 30 ≤ d < 60 | d ≥ 60 |

同一客户命中多个真实规则时取最高关注等级、仅统计一次客户，并保留不同真实原因；同一间隔事实不能换名称重复算成独立风险。不累加为预测分数，也不输出概率。

### 5.3 从未跟进：默认阈值与特殊状态

确实没有有效或异常CUSTOMER跟进历史的客户，以customer.created_at为时间锚点，a为建档后的完整24小时天数，所有客户等级使用下表：

| 建档年龄 | 结果 | 类型 |
|---|---|---|
| a < 7 | 观察中 | 特殊状态，不是正常风险等级 |
| 7 ≤ a < 14 | 中关注 | 正常风险等级 |
| a ≥ 14 | 高关注 | 正常风险等级 |

- 不把建档时间填成最后跟进时间，必须明确“从未跟进”；这是新建未首次跟进，不是新分配未跟进。
- 只有异常历史：数据待核验，不进行正常风险分级；不能用建档年龄绕过该状态判高关注。
- 有有效历史且有异常历史：按有效历史使用第5.2节分级，同时保留数据质量提示；不因存在异常就丢弃有效结果或自动升高等级。
- 未来跟进、早于客户建档等异常不直接用于正常风险计算。异常具体分类、提示和非正常结果展示留D1设计，不能改变以上分级分流。
- 未评级保留原值，有有效历史按B/C/D同组阈值计算；无历史按建档7/14天规则计算。
- next_follow_at是否存在都不参与本版分级或排序，不回退历史计划推断未履约。
- 联系人为空、跟进人与当前负责人不同可能是正常情况，不仅因这些字段就增加关注等级。
- 负责人删除/停用、无部门、未知状态或权限配置不清时不得扩大范围；仅POTENTIAL/ACTIVE属于适用状态。受控错误与数据质量提示的协议细节由D1明确，不改变准入和适用集合。

### 5.4 计划语义：明确排除

当前仅有历史记录上的next_follow_at，没有计划ID、状态、完成/取消时间或归属交接事件。最新记录有计划、最新非空计划、全部历史计划是不同集合；实测分别出现52个最新有计划客户、152个历史有计划客户。

V2.0不支持计划逾期正式判定，不因时间已过生成计划逾期风险原因，也不由模型补出完成/取消结论。报告保留字段可计算性的历史调查，不表示纳入本版范围；需要该能力时另立需求。

### 5.5 后端规则配置与版本一致性

- 第5.2节14/30、30/60天和第5.3节7/14天是当前V2.0已确认的默认值，必须由后端配置管理，不能由前端或Qwen自行覆盖。
- 必须记录规则版本，使其可追溯到该版本完整阈值及分级配置；影响判定的配置变更不得悄然沿用同一版本而产生不同解释。
- 单次分析固定一套一致的规则版本和阈值；原因、分级、超期天数、排序、计数及当前页建议使用同一基线，不混合新旧配置。
- 同一分析时间T、数据快照及规则版本下，Java结果具有确定性。Qwen文案不承担判定一致性，不能改变结果；跨请求如何保持快照及分页一致性留D1设计。
- 配置缺失/非法或版本映射不一致时须受控处理，不静默以部分默认值拼接出不可追溯规则。配置文件结构、版本标识形式、加载/校验机制由D1决定，不在本PRD冻结Java类名。

## 6. 权限与安全需求

- 对第3.1节的单有效销售角色及三权限先执行V2准入，再解析范围；管理员和多角色不得借V1默认CURRENT_AUTHORIZED旁路准入。
- SALES_STAFF SELF、SALES_MANAGER DEPT/SELF的范围语义可复用V1.1；DataScopeResolver及策略的最大/请求/实际范围分离继续有效，但现有策略硬绑定customer:list且允许管理员ALL，**不是完整V2门禁**。
- 三权限明确为ai:analysis、customer:list、follow:list，同时具备才可进入V2；不因拥有customer:list读取全部跟进详情。本次不新增权限码、不修改角色绑定，也不改V1/V1.1权限要求。
- 客户清单、聚合、分页总数、原因、建议及相关历史都以获准客户集合为边界；单客户请求重新检查当前对象可见性，越界ID不返回指标或正文。
- 不以follow_record.owner_id替代customer.owner_id做SELF，也不以跟进人的部门替代客户负责人的部门做DEPT。
- 业务工具独立复核权限及范围；模型只能提出受控意图/合法参数，不能提供可信身份、授权上下文或SQL，不得从文本中执行写动作。
- 当前建议只使用必要结构化指标，不默认向模型提供正文/备注全文、联系方式、详细地址等非必要敏感信息；所有业务数据均不是可信指令，防止提示注入，不在日志或结果中暴露凭据。
- 建议、原因和排序所引用的事实必须可回查，不由模型新增风险等级。对凭证、正文、跨部门客户以及模型服务故障有受控错误，不泄露内部SQL/堆栈。

## 7. 数据需求与质量限制

所需字段及逐字段类型/可空性见[可行性报告第2–3节](AI_AGENT_V2_FEASIBILITY_REPORT.md#2-客户字段可用性)。必要集合为客户id/名称/等级/owner/status/created_at/deleted，跟进target_type/target_id/follow_at/deleted；建议只使用所需结构化指标，next_follow_at不是本版分级依据。

2026-10-18实测有效客户327（已分配290、公海37）、跟进1,236；已分配客户有跟进285、无跟进5。全部记录有follow_at，36条与录入时间不同。基础字段足够做首版指标，但没有分配时间与计划完成状态。

R1原始样本无删除客户、未来跟进、孤立关联、交接差异等典型异常，不能视为异常路径已验证。原报告7/14/30/60天敏感性观察包含全部已分配客户与所有状态，不是本次冻结分等级规则后的风险结果。固定基准日合成数据已老化，不能据此宣称阈值的真实经营有效性；业务默认值由三轮评审确认。原始明细不进入需求文档，不为校准修改数据。

原质量统计包含49个已分配INACTIVE客户，V2.0正式适用集合必须排除它们；报告327/290等原始总量仍保留，但不能冒充正式风险查询的匹配数。未评级15个已分配客户不是缺失必填字段错误。正式过滤和冻结规则下的分级数量留后续实现独立SQL验证，本次不重算历史统计。

## 8. 非功能需求与工程约束

- 可解释：显示规则、版本、观测值、当前阈值、T及数据质量；不得以“模型认为”代替原因。
- 一致：同快照/规则/时间产生相同Java结果；多规则不重复计客户，分页稳定；权限/归属变化后旧结果不成为新请求授权凭据。
- 可靠：数据库错误、权限缺失与无匹配分开；建议失败不篡改主结果，返回可理解的部分不可用状态。具体API契约留D1，不改变V1现有契约。
- 安全：最小化数据进入模型和日志，所有读取均由后端强制校验；数据库和模型查询的资源边界、超时及重试策略由D1评估，不擅自复用V1最多两次模型调用作为V2冻结指标。
- 性能：已确定每页默认20、最大50，建议仅针对当前页必要结果；需评估范围内客户数、历史记录量、批量查询、模型输入规模及并发，不采用无界逐客户查询或模型调用。输入令牌预算、数据库响应和整体SLA、并发限额留D1实测，本阶段不编造性能结论或索引方案。

## 9. 需求边界

V2.0支持当前风险快照、关注客户列表、单客户原因、辅助建议、合法SELF/DEPT范围、分页及结构化展示。默认关注查询只返回高/中关注，明确全状态查询按第4.3节处理，始终限定POTENTIAL/ACTIVE有效已分配客户。

不包含历史风险回溯、计划逾期正式判定、流失/成交概率预测、机器学习训练、跨部门任意人员查询、INACTIVE或公海风险分析、自动分配/转移/领取、跟进写入或自动执行建议。

不实施联系人/跟进完整CRUD，不假设已存在详情跳转；只读业务能力和对象授权是必须补齐的依赖。暂无分配事件时不支持新分配风险。首版不引入RAG、向量库、多Agent、对话持久化、多轮记忆或其他范围外方案。

自然语言需要覆盖“关注清单”“单客户原因”“跟进建议”等新语义，V1两个统计意图和统计Tool不足以承载；需受控只读业务工具与结构化事实交互，但R1不确定枚举名、类名、工具签名、调用次数、表结构或API路径。

## 10. 验收标准

以下为V2.0实现后的验收要求；本次仅维护需求文档，没有开发或执行V2测试，不能标记为已通过。

| 场景 | 必须验证的行为 |
|---|---|
| 正常销售与经理查询 | 销售仅SELF；经理默认DEPT、可显式SELF；范围按当前owner/负责人部门过滤，与独立SQL一致 |
| 角色/权限拒绝 | 缺任一三权限、两类管理员、多有效/未知角色、角色范围配置异常均拒绝；默认请求也不可旁路，无明细泄露 |
| 单客户越界请求 | 即使已知ID/旧会话/分页游标，也重新对象授权，不返回跟进事实 |
| 时间字段不同 | follow_at与created_at不同，仍按业务时间计算；updated_at不作替代 |
| 已有历史分级 | A级14天中、30天高；B/C/D/未评级30天中、60天高；低于中阈值均低关注 |
| 无历史分级 | 建档不足7天观察中，达到7天中、14天高；不伪造最后跟进时间 |
| 异常历史分流 | 仅异常历史为数据待核验且不正常分级；有效+异常按有效历史分级并保留质量提示 |
| 临界值 | 对7/14/30/60天及实际分组覆盖阈值前、等于、后和跨自然日；统一T与完整24小时，异常不得参与正常判定 |
| 多规则与缺等级 | 一客户只计一次、取最高等级，保留不同真实原因、不重复同事实；未评级按B/C/D组阈值 |
| 历史归属差异 | 包含获准客户全部有效历史（含前负责人），不因跟进人不同漏算或越权 |
| 适用集合/多态 | 默认及全状态均排除INACTIVE、公海、删除客户/记录，仅POTENTIAL/ACTIVE；同target_id不同target_type不串用 |
| 计划边界 | 无论最新计划为空、历史非空或已过时间，均不产生本版计划逾期正式判定 |
| 排序与超期 | 等级→客户等级→本等级起始阈值超期天数降序→ID稳定排序；阈值刚命中超期为0，无负值/无限大 |
| 查询模式与分页 | 默认只匹配高/中关注；全状态可展示低关注/观察中/待核验，20默认、50上限；先筛选排序计数再分页 |
| 配置与版本 | 默认14/30、30/60、7/14正确，配置可追溯至规则版本；同T/快照/版本确定，单次不混新旧配置 |
| 建议事实一致性 | 注入/虚构客户ID、日期、指标、等级均不改变可信结果；无写操作 |
| 空结果/故障 | 真无匹配可空，权限/SQL失败不能伪装0；模型建议失败保留规则结果并标不可用 |
| 展示及限额 | 范围/T/规则/当前条数与总数清晰，截断不能冒充全部，无不必要敏感字段 |
| 规模与回归 | 达成评审后性能预算；V1/V1.1统计、范围及错误契约不退化 |

真实数据库缺少的异常样本在后续授权测试环境准备，不在R1插入或修复。单元测试、独立SQL、真实模型/浏览器验证须分别记录，不互相冒充。

## 11. 已确认决策与D1设计事项

### 11.1 三轮评审决策摘要

角色与三权限、第5节适用集合/时间/分级及特殊状态、多规则取最高、排序、默认高/中筛选和20/50分页、最小结构化模型输入及失败保留结果均已确认，不再是待评审选项。计划逾期正式判定、历史回溯等已明确排除。业务矩阵、阈值与排序以第3–5节为唯一详细规则主表。

### 11.2 仍需D1确定的技术设计

1. V2准入与V1.1范围组件的复用边界、三权限和对象授权的落点；保留V1/V1.1接口语义，不把管理员ALL或多角色默认语义带入V2。
2. 只读数据能力、有效/异常历史识别、客户集合与聚合/排序/总数/分页一致性；同T多请求的数据快照与权限变化处理。
3. DTO/VO、API路径、受控意图、Tool边界与合法参数、错误协议及部分建议失败的表达；不在本阶段指定类或方法签名。
4. 规则配置结构、版本追溯及一致加载校验；事实保护、模型输入最小化、当前页建议组织与输出校验。
5. 正常结果ID升降方向、特殊状态在全状态查询中的分区/展示次序、同业务时间记录与异常提示的确定性工程约定；不改变已冻结的正常风险排序优先级。
6. 自然语言“优先跟进”“全部关注状态”和具体等级条件的识别、澄清及范围外请求拒绝，不能把“全部”默认为ALL或纳入INACTIVE。

### 11.3 尚需实测的性能与工程约束

- 缺失异常样本、阈值边界、规则配置切换、对象范围变化、分页稳定及建议事实校验的测试数据和验证方法。
